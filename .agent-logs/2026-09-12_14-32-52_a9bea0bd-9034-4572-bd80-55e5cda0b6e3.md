The pipeline is further along than last session — there's now a pull-based work queue ([lib/jobs.ts](frontend/src/lib/jobs.ts)) and a runner loop ([watch.ts](backend/src/watch.ts)), so a bot on your laptop claims jobs from the deployed app over outbound HTTPS. ## What's actually wrong with it

I traced the whole path. These are real, not stylistic:

**The transcript is posted before the meeting happens.** [session.ts:216](backend/src/session.ts#L216) calls `recordStubTranscript` (which sleeps 30–60s) and POSTs immediately — *then* calls `monitorCall`. So the app receives the "final" transcript about a minute into a call that runs another 40. Everything after that point is never captured or sent. This is the single biggest structural problem: there is no post-call phase, only an early-call one.

**The summary never reaches the app.** [api/bot/transcript](frontend/src/app/api/bot/transcript/route.ts) destructures `summary` from the body, passes it to `saveBotTranscript`, and [data.ts:354](frontend/src/lib/data.ts#L354) accepts it in the signature and then never writes it. Nothing touches `COLLECTIONS.summaries`. So the summary exists in Meet chat and nowhere else — the UI shows a bot meeting with no summary.

**Analytics are never computed.** `computeAnalytics` exists and the seed path uses it, but `saveBotTranscript` skips it, so the talk-time ribbon is empty for every bot-recorded meeting.

**Re-running the same meeting 500s.** `saveBotTranscript` uses `insertOne` with `id: meetingCode`. My seed script put a unique index on `meetings.id`, so the second run throws a duplicate-key error, gets swallowed by the catch, returns `null`, and the route reports a generic 500. A recurring weekly standup has the same Meet code every week — this is the normal case, not an edge case.

**`resultMeetingId` is never set.** The field exists on `BotJob`, `watch.ts`'s `report()` accepts it, `updateJob` persists it — but nothing ever sends it. So a finished job can't link to the meeting it produced.

**Speaker names are thrown away.** `transcription.ts` tracks real participant names; `saveBotTranscript` relabels everyone `Speaker 1`, `Speaker 2`.

**The ingest route is unauthenticated.** `/api/bot/jobs/next` and `/api/bot/jobs/[id]` check `isAuthorisedRunner`; `/api/bot/transcript` does not. Anyone who finds the URL can inject a transcript.

**The job title is discarded.** Jobs carry `title`, but meetings get named `Bot Recording: abc-defg-hij`.

Also minor: `durationMs` comes from the last turn's `endMs` rather than actual time in call, and the transcript POST is hardcoded to `http://localhost:3000` despite `options.appUrl` existing.

**M1 — Move capture to the end of the call.** Split `recordStubTranscript` so the recording spans `monitorCall` instead of preceding it, and POST results after the call winds down. Use `options.appUrl`, not localhost. Send `resultMeetingId` back on the job. *This unblocks everything else — the other milestones are cosmetic until the bot reports at the right time.*

**M4 — Surface it in the UI.** Post-call state currently only lives in [IntegrationsPanel](frontend/src/components/settings/IntegrationsPanel.tsx). A finished job should link to its meeting, and a bot-recorded meeting should be visibly distinguishable from seeded ones.

M1 and M2 are where the substance is; I'd do them together since M2's write is what M1 calls at the right moment. M3 is ~20 min, M4 is UI work and easiest to cut.
