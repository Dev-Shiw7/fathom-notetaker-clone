Good question to push on — this is the decision with the longest shadow. Let me lay it out concretely.

## 1. Implementation difference

The launch API itself changes shape, which ripples into cleanup:

```ts
// GUEST — what we have now
const browser = await chromium.launch({ channel: 'chrome', headless, args });
const context = await browser.newContext({ permissions, locale, viewport });
const page    = await context.newPage();
// teardown:
await browser.close();

// PERSISTENT — one call, launch opts + context opts merged, no Browser handle
const context = await chromium.launchPersistentContext(profileDir, {
  channel: 'chrome', headless, args,      // launch options
  permissions, locale, viewport,           // context options
});
const page = context.pages()[0] ?? await context.newPage();
// teardown:
await context.close();
```

That forces `LaunchResult` to normalize over both, and it has a non-obvious consequence: **Chrome locks the profile directory**, so two bots cannot share one profile. Concurrency needs a profile dir per bot, or copy-a-template-per-run.

## 2. The join flow diverges

| Step | Guest | Signed-in |
|---|---|---|
| Name entry | **Required** — types into `input[aria-label="Your name"]` | **Absent** — name comes from the account |
| Join button | Always `Ask to join` | `Join now` if invited/in-org, else `Ask to join` |
| Waiting room | **Always** | **Skippable** when invited to the calendar event |
| Onboarding overlays | Rare | Common — "Got it" dismissal needed |
| Org-restricted meetings | Hard fail | Works if the account is in the org |

So `prejoin.ts` needs a conditional branch, not one linear path.

## 3. Trade-offs

**Guest join**
- ✅ Zero auth infra, no secrets, nothing to rotate or expire
- ✅ Stateless → trivially parallel, N containers with no shared state
- ✅ No Google account to get flagged or suspended for automation
- ✅ Already built and working
- ❌ **Always needs a human to admit it** — unattended operation is impossible
- ❌ Cannot enter org-restricted meetings at all
- ❌ Unverified arbitrary name — reads as sketchy to participants
- ❌ **Calendar auto-join is structurally impossible** — a guest can't be invited

**Persistent login**
- ✅ Can be **invited to the calendar event → auto-admitted, no human** — this is the whole unattended product
- ✅ Reaches org-restricted meetings
- ✅ Real identity with avatar; looks legitimate in the participant list
- ✅ Required for the calendar auto-join milestone already in our architecture
- ✅ What actual products do — Fathom has you connect an account
- ❌ One-time manual sign-in; Google reliably blocks *automated* sign-in
- ❌ **Profile goes stale** — session expiry, device challenges, "unusual activity" flags
- ❌ Profile dir is a live secret (session cookies) — never commit, needs secure storage in prod
- ❌ Profile lock → one bot per profile dir
- ❌ Onboarding overlays to dismiss

## 4. Which is better

It splits by axis, so the honest answer isn't one-sided:

| Axis | Winner |
|---|---|
| Fastest to a working demo | **Guest** — already built |
| Fewest things that break *on demo day* | **Guest** — no re-auth challenge mid-demo |
| Correct for the actual product | **Persistent** — decisively |
| Unattended / scheduled operation | **Persistent** — guest literally cannot |
| Scaling to many concurrent bots | **Guest** — stateless |
| What BUILD_PLAN mandates | **Persistent** |

**My recommendation: persistent as primary, guest as automatic fallback.**

The reasoning is that the marginal cost is genuinely small right now. `inspect` has to be built anyway — Hour 3's caption-selector work depends on it — and `inspect` *is* the sign-in mechanism. So persistent login costs roughly: the launch-shape normalization, a profile-dir config flag, and a conditional name-entry branch in prejoin. Call it 40 lines.

And the fallback earns its keep on demo day: if the profile has gone stale, a hybrid bot degrades to "needs manual admission" — which is exactly the demo you were going to run anyway — instead of failing outright. A pure-persistent bot with an expired session just dies.

The thing that settles it beyond the assessment: **guest join cannot do calendar auto-join**, and that's not a feature we listed for politeness — it's the difference between a notetaker and a screen-recorder. Building on guest means rebuilding this layer the moment we add scheduling.

One caveat worth stating plainly: driving a Google account with automation is against Google's ToS and the account can get flagged. That's why BUILD_PLAN says *dedicated* account, not your personal one — and it's a real argument for why a production system buys Recall.ai rather than maintaining this.

Want me to build it hybrid (persistent primary, guest fallback), or straight persistent-only per BUILD_PLAN?

Good question, and it changes my recommendation.

## What "per-turn audio" meant

One `.m4a` file per transcript turn — `turn-0042.m4a` holds just *"Priya: Let's start with pipeline review."* The player keeps a queue and starts the next file when one ends.

I only proposed it because there's no `ffmpeg` here to join clips together. It has real downsides:

- Scrubbing to an arbitrary point (23:41) means computing which turn contains it, loading that file, then offsetting into it
- Hundreds of HTTP requests per meeting
- Audible seams between clips
- Native `<audio>` scrubbing doesn't work — I'd hand-roll it

## ffmpeg is only ever a build-time tool

**Deployment never touches it, and no Docker is involved.** The chain is:

```
your Mac:   say → afconvert → ffmpeg concat → public/audio/<meeting>.m4a   (once)
Render:     serves that .m4a as a static file                             (forever)
```

Render runs Next.js as a plain Node web service. Audio files are static assets like images. Nothing at runtime knows ffmpeg exists.

## So yes — get ffmpeg, it's clearly better

| | Stitched (with ffmpeg) | Per-turn (without) |
|---|---|---|
| Scrubbing | Native `<audio currentTime>` | Hand-rolled queue + offset math |
| Requests/meeting | 1 | 300+ |
| Playback | Seamless | Audible seams |
| Files in repo | ~10 | ~1500 |
| Timestamp accuracy | **Exact** — derived from real clip durations | Exact |

The accuracy point is worth spelling out: I generate each turn, read its true duration with `afinfo`, accumulate offsets, *then* concatenate. So transcript timings come from the actual audio rather than being guessed — which is the property that makes click-to-seek and action-item deep-links genuinely trustworthy.

```

```

One trade-off to flag: an hour of mono AAC is roughly 28MB, so all ten meetings land around 40–60MB committed to the repo. Git and Render both handle that fine, it just makes the clone chunky. The alternative is hosting audio on S3/Cloudinary, which is more setup for no visible benefit on a demo.
